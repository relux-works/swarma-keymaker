# Static gate vectors

Vectors for [`swarma-s7 static-gate/1`](../../spec/keymaker-static-gate.md).
Every value is invented or published test data. The statements are signed
with CSV indices 1, 2 and 3 of the published BIP-340 test vectors; those keys are public
and must never approve anything real. The contents of `broker_time` and
`broker_d5` are placeholders, because their owner has not frozen them.

| File | Contents |
| --- | --- |
| `genuine.ccj` | The genuine statement: exact CCJ-1 bytes, no final LF |
| `genuine.sig` | Its wire signature: 128 lowercase hex characters, no final LF |
| `vectors.json` | Every positive control, negative and stated limit |

Each row of `vectors.json` is self-contained:

| Member | Meaning |
| --- | --- |
| `id`, `claim` | Stable name and the one claim the row proves |
| `expect` | `pass` or the exact refusal code |
| `checks` | For a negative: the verifier checks that refuse it. The first is the one that fires; the others would refuse it if the first were absent |
| `control` | For a negative: the `id` of the passing row it stands beside |
| `limit` | `true` for a stated limit: a pass that is not protection |
| `statement_hex` | The exact statement bytes |
| `signature` | The wire signature text, exactly as supplied |
| `inputs` | `approver_key`, `statement_digest`, `machine_id_sha256` (hex), `now` (RFC 3339), `class`, `consumer`, and the expected `section` and `association` bytes as text |

Negatives are signed by the approver key and pinned by their own digest unless
the row is about the key, the pin or the signature. That way each row is
refused by the one check it names and not by an earlier one. Most rows
self-pin by design: `statement_digest` is computed from that row's bytes to
isolate later checks, not an example of how a consumer obtains its protected
pin. `ExampleVerify` instead uses a literal expected digest.

Every negative has a passing neighbour of the same consumer, except the two
invalid-consumer inputs: only the consumer field changes from a valid
consumer because no positive can use an invalid one. Input-only negatives
keep the same raw bytes and signature and change exactly one input field;
the suite enforces this mechanically. The `order-` rows intentionally combine
faults to pin refusal precedence, and unusable-key rows match the pin to the
invalid key to reach `SIGNATURE`.

UID examples use 30000..59999 (apart from explicit UID-shape negatives).
Association and worker generation examples are 32 lowercase hex digits
(apart from the explicit empty-generation negative); non-hex and Unicode
section generations demonstrate that the verifier stays opaque. Consumers
such as M0 impose their own stricter shapes.

The file is generated by `go test ./staticgate/...`, which also checks it
byte for byte and runs every row. To regenerate after a format change:

```sh
STATICGATE_WRITE_VECTORS=1 go test ./staticgate/... -count=1
```

The set has 180 rows: 21 passes and 159 refusals. `end-zero-now` and
`window-zero-now-start` both refuse with `STATIC_GATE_WINDOW`; their passing
neighbours keep the same consumer, statement bytes and signature with real
clock readings. Six `form-host-machine-id-*` rows pin malformed host digest
shapes to `STATIC_GATE_FORM` before the later host-binding check.

An implementation in another language can run the rows directly: decode
`statement_hex`, apply the consumer rule with `inputs`, and compare the result
with `expect`.
